# AGENTS.md

Single-file Python project: `harnless.py` — a minimal CLI agent harness that talks to a local llama-server (OpenAI-compatible API) and exposes file/bash tools. Stdlib only; no dependencies, no venv, no build step.

## Requirements

- A running LLM server for the agent to talk to. Default endpoint is `http://127.0.0.1:11434/v1/chat/completions` (`API_URL` in `harnless.py:14`), overridable via `--api-url`. Tests (`tests.py`) don't need a server.

## Commands

- Interactive: `python harnless.py` (chat REPL; typing `/` on an empty line opens a command menu (up/down move, enter select, esc cancel — a selection fills the line, a cancel keeps the `/`), `/new` clears session history, `/clear-screen` clears the terminal, `/tools` opens an interactive tool menu (up/down move, space toggle, enter apply, esc cancel) and `/tools <name>` toggles a tool on/off, `/exit` quits)
- One-shot: `python harnless.py --prompt "task"` (exits with the agent's exit code)
- Flags: `--api-url` (OpenAI-compatible API URL; accepts either a base URL like `https://openrouter.ai/api/v1` or a full `.../chat/completions` endpoint — a base URL gets `/chat/completions` appended; default `http://127.0.0.1:11434/v1/chat/completions`), `--api-key` (sent as `Authorization: Bearer <key>`; omit for unauthenticated local servers), `--model` (name sent in the request; llama-server ignores it), `--system-prompt` (replaces built-in), `--temperature` (sampling temperature; default `0.2`), `--max-subagents` (max sub-agent nesting depth for the `task` tool; default `3`), `--context-window` (model context window size in tokens, shown as a percentage in `/status`; if omitted, probed best-effort from the API's `/models` endpoint — `context_length` (OpenAI/OpenRouter) or `meta.n_ctx` (llama.cpp) — and hidden if the probe fails), `--version` (print `harnless <version>` and exit; the version also appears in the REPL/one-shot startup banners)
- MCP servers (tools only): `--mcp-config FILE` (repeatable; JSON `{"mcpServers": {...}}` or a bare `{...}`), `--mcp-stdio 'NAME:COMMAND ARGS...'`, `--mcp-http 'NAME=URL'`. `${VAR}` in a config is expanded from the environment. A server that fails to connect/list tools is skipped with a warning.
- `AGENTS.md` in the working directory (case-insensitive) is auto-loaded and appended to the system prompt in all modes.
- Interactive-mode input history is persisted to `~/.harnless_history` (last 1000 entries, one per line); path overridable via the `HARNLESS_HISTORY` env var.
- Multi-line REPL input: Ctrl+J inserts a newline into the current line (Enter submits). The key iterators yield a `newline` token for `\n` (Ctrl+J) vs `enter` for `\r`; `_edit_line` inserts `\n` at the cursor and `render()` redraws multi-line input with ANSI cursor moves + `\x1b[2K` (no newlines, so the screen never scrolls). The non-TTY `input()` fallback stays line-based.
- Streaming interrupt: in the REPL, pressing ESC twice within 2 s while the LLM is streaming cancels the generation (a lone ESC prints a hint) — it also works while the context is being sent, aborting the upload itself. The partial assistant message is kept in the conversation (any half-formed `tool_calls` are stripped; partials left without `content` — e.g. interrupted mid-thinking — are dropped, since servers reject assistant messages with neither content nor tool_calls) and the agent returns to the prompt. Works while sub-agents stream too (the innermost stream is interrupted).
- Tests: `python tests.py` — stdlib unittest, no pytest. Must run from repo root; uses a temp `./_test_tmp` dir (cleaned up); exit code 1 on failure.

## Notes

- `tests.py` imports the module directly (`import harnless`).
- Tools are defined once in the `TOOLS` dict (`harnless.py:961`): each entry is `(OpenAI schema, handler)`. `OPENAI_TOOLS`/`DISPATCH` are derived from it — add new tools there. `OPENAI_TOOLS_INTERACTIVE` (same minus `exit`) is sent to the API in interactive mode; `exit` stays one-shot only.
- Output capping (v1.2.0): two layers. Model-facing limit args — `grep.limit`, `glob.limit`, `list_dir.limit`, `read_file.max_chars`, `run_shell.max_output`, `fetch_url.max_chars` — are read by `_limit_arg` and clamped to `[1, ceiling]`; defaults/ceilings are the `*_LIMIT` constants in the constants block near `harnless.py:49`. `TOOL_RESULT_LIMIT` (60k) is the final backstop in `execute_tool` and must stay **above** every per-tool cap, otherwise a tool that already trimmed gets a second note (`test_cap_constants_are_ordered` guards the ordering). All truncation goes through `_truncate` / `_cap_count` / `_cap_note` (the "output caps" section above the tools) which append `\n... [truncated: <stat>; <recovery hint>]` — keep that one format so both tests and the model can rely on it. `grep` additionally clips every matched line at `GREP_LINE_LIMIT` (`_clip_line`, kills minified-file megadumps) and caps total output at `GREP_TEXT_LIMIT`. Paths that were uncapped before are now capped: `task`'s sub-agent summary, `_mcp_content_to_text` (incl. `structuredContent`), `_todo_block` (tool output + `_todo_reminder`; `_todo_render`/`_todo_save` stay uncapped so `.harnless/todo.md` keeps the full list), `tool_memory` list + `load_memory` (this block feeds every system prompt), and `load_agents_md`.
- State tools: `todo` (in-memory list persisted to `.harnless/todo.md`; after each tool batch, `_todo_reminder` re-injects a reminder (as a **user** message, not system — some templates like Qwen forbid system messages anywhere but the first position) with the current list into the conversation when it changes — `TODO_LAST_INJECTED` is saved/restored around sub-agent runs so the parent sees sub-agent edits) and `memory` (persistent notes in `.harnless/memory.md` (project) and `~/.harnless/memory.md` (global); one-line pitfall notes belong here too, prefixed `gotcha: ` — the separate `gotcha` tool and `.harnless/gotchas.md` were removed in v1.1.0). Memory is loaded into the system prompt at startup via `_context_additions` (also for sub-agents); the todo list is loaded at startup via `_todo_load`.
- Sub-agents: the built-in `task` tool (`tool_task`) delegates a self-contained task to a nested `run_agent` with a fresh context (sub-agent system prompt + AGENTS.md, full one-shot tool set). It returns the sub-agent's exit code + final summary as the tool result. Depth is tracked in `_AGENT_DEPTH` (set at `run_agent` entry) and capped at `MAX_SUBAGENT_DEPTH` (`--max-subagents`, default 3); sub-agents can delegate further until the cap. Sub-agent output is printed live, indented 2 spaces per level via `OUTPUT_INDENT`. `run_agent` returns the `exit` tool's code instead of calling `sys.exit` (the one-shot path in `main` does `sys.exit(run_agent(...))`), which is what lets a sub-agent's `exit` end only the sub-loop.
- MCP tools are discovered at startup (`register_mcp_tools`) and registered into `MCP_TOOLS`/`MCP_DISPATCH` (not `TOOLS`). They use raw names; a name colliding with a built-in tool or an earlier MCP server is skipped (built-ins win, then first server). MCP tools are external and bypass the `safe_resolve` sandbox.
- All tool file paths are relative to CWD and must stay inside it (`safe_resolve`, `harnless.py:224`); never weaken this. CWD itself may be a symlink/junction: `_cwd_roots()` (`harnless.py:176`) returns CWD plus its `realpath`, `_inside_cwd` checks containment case-insensitively (`os.path.normcase`) against both, and `grep`/`glob` print paths with `_rel_to_cwd` (`harnless.py:205`) so they stay CWD-relative (`src/main.py`, not `../../../real/src/main.py`). `safe_resolve` still returns the realpath, and a link *inside* CWD that points outside is still rejected.
- Glob patterns (`glob` tool, `grep` `file_pattern`) are compiled by `_glob_to_regex` (`harnless.py:238`) against the whole CWD-relative path: `**/` matches zero or more directories (so `**/*.py` matches root-level files too), plain `*`/`?` cross `/`, and a pattern containing `[](){}|\^$` is used as a raw regex.
- `patch_file` supports an optional `offset`/`lines` region to disambiguate duplicate `old_string` matches; `write_file` with `offset` does line-range replace/insert (semantics covered by `tests.py` — run it after touching those functions).
- `/status` context usage: prefers the server-reported `usage.prompt_tokens` from the last API response (non-streaming responses include `usage`; streaming requests send `stream_options: {include_usage: true}` and the final SSE chunk carries it — `parse_sse_line` returns a `{"usage": ...}` marker for that chunk, which `stream_chat` records instead of yielding). Usage is stored per conversation in `USAGE_BY_CONV` keyed by `id(messages)` (via `_record_usage`), so sub-agents track their own context. Falls back to a chars/4 estimate (labeled "estimated") when no server usage is available yet (e.g. before the first response).
- Assistant output is styled by `MarkdownRenderer` (`harnless.py`), which supports headings, lists, blockquotes, fenced code, inline emphasis/code/links, and pipe tables (box-drawing borders, `:--`/`:-:`/`--:` alignment, inline styling in cells, terminal-width clamping). Tables are buffered whole before printing (a `|` line is held one line to test for a delimiter row); with colors disabled the raw Markdown passes through unchanged.
- Context progress: for large requests (estimated ≥ `CONTEXT_PROGRESS_THRESHOLD` = 30,000 tokens via `estimate_context_tokens`, chars/4 including the tool schemas — the same heuristic `/status` uses), `ContextProgress` shows a line on a daemon thread while waiting for the LLM's first token (streaming) or the full response (non-streaming `chat()` fallback). It appears `CONTEXT_PROGRESS_DELAY` (1 s) in, updates every 0.5 s, and is cleared (ANSI) when the wait ends. Two states: while the request body is uploading it shows `⏳ sending context… 45% (14.4k/32.4k tokens) 3s` (percent + tokens sent so far, from a `_UploadProgress` counter fed by `_progress_opener` — a urllib opener whose HTTP(S) connections send the body in `PROGRESS_CHUNK` pieces instead of one `sendall`); once uploaded it shows `⏳ waiting for first token (32.4k tokens) 12s`. Only active when stdout is a TTY (small contexts and non-TTY never start the thread, so tests/mocks of `urlopen` are unaffected). If the double-ESC hint prints below the line (`InterruptWatcher.on_hint` → `note_lines_below(2)`), the line freezes so a redraw can't clobber it, and `stop()` moves up to clear the right line.
- Streaming interrupt mechanics: `INTERRUPT_ENABLED` is set in `main()` for REPL sessions with a TTY stdin (one-shot mode never interrupts). Each streaming turn, `stream_once` starts an `InterruptWatcher` — a daemon thread running the polling key iterators (`_iter_keys_windows_poll`/`_iter_keys_posix_poll`, which poll `kbhit`/`select` so the thread can be stopped without a keypress). `check_double_esc` (pure, testable) detects two ESCs within `DOUBLE_ESC_WINDOW`; on trigger the watcher closes the response socket (`_response_socket` digs out the socket, trying both `resp.fp.fp.raw._sock` (older Pythons, `fp` is a `SocketFile`) and `resp.fp.raw._sock` (Python 3.14+, where `fp` is the `BufferedReader` directly)) so the main thread's blocked read unblocks — `close()`, not `shutdown()`, is what unblocks a pending `recv` on Windows — and sets `triggered`. The upload socket is attached too: `stream_chat` passes `watcher.attach_socket` as `_open_request`'s `on_socket`, and the counting connection reports it via `upload.on_socket` as soon as `connect()` completes, so a double ESC during the context send closes the socket mid-send and `stream_chat` swallows the resulting send error (the turn then ends via the same `StreamInterrupted` path). `stream_chat` checks `watcher.triggered` between deltas and swallows the resulting read error; `stream_once` finalizes the renderer, prints `(interrupted)`, and raises `StreamInterrupted` (carrying the partial message), which `run_agent` handles (strip `tool_calls`, append the partial only if it has `content`, return 0).
